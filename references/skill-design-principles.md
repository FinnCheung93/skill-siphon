# Skill Design Principles

本文件吸收 `writing-great-skills` 的可迁移精华，用于审查、优化或吸收其它 Codex skills。它是按需读取的设计 reference，不是 `SKILL.md` 主流程。

## 1. 根目标：过程可预测性

好 skill 的根目标是让随机系统产生更可预测的过程。可预测不是输出一致，而是 agent 每次都按同一类可靠路径行动：先判断该不该用、再读取必要材料、再按合适步骤推进、最后按明确标准收尾。

所有设计判断都服务这个目标：触发、拆分、引用、完成标准、术语、修剪和失败处理。

## 2. 调用取舍

skill 有两类调用成本：

| 类型 | 价值 | 成本 | 适用判断 |
|---|---|---|---|
| model-invoked | agent 可自动发现，也可被其它 skill 触达 | `description` 常驻上下文 | agent 需要主动识别该能力，或其它 skill 需要调用它 |
| user-invoked | 不消耗模型常驻上下文 | 用户必须记得它存在 | 只应由用户手动点名，或需要保留人为裁决入口 |

当 user-invoked skill 太多、用户记不住时，可考虑一个 router skill：它不亲自做所有事，只帮助用户选择该用哪个 skill。

机制判断：

- 有 model-facing `description` 且未禁用 model invocation：按 model-invoked 审查。
- 设置 `disable-model-invocation: true`：按 user-invoked 审查，`description` 更像人类摘要，不应承担复杂触发分支。
- 不存在只有 model 能调用、用户不能调用的状态；model-invoked 只是增加 agent discovery。

## 3. Description 写法

`description` 是 model-invoked skill 的触发器，也是常驻上下文成本。它应承担触发分支，不承担正文解释。

检查点：

- 开头放最能触发该 skill 的 leading word 或核心动词。
- 一个真实触发分支写一次；同义改写不应重复堆叠。
- 删除正文里已经能说明的身份介绍。
- 只保留触发条件、使用条件、跳过条件，以及“其它 skill 何时需要它”的 reach 条件。

## 4. 信息层级

skill 内容应放在合适层级。注意：不是所有 skill 都必须有步骤；纯 reference skill 可以完全成立。

1. `SKILL.md` 中的步骤：agent 必须按顺序执行的动作。
2. `SKILL.md` 中的内联 reference：高频、所有路径都需要的规则或定义。
3. 外部 reference：只在某些分支、深挖或审查时需要的定义、模板、长规则和例子。

判断方式：

- 每条路径都需要的内容可内联。
- 只有某些分支需要的内容应渐进式披露。
- 必要内容没被读取时，优先修 context pointer 的文字，而不是立刻把所有内容塞回主文件。
- 一个概念的定义、规则和注意事项应尽量共置，避免散落在多个地方。
- 对 reference-only skill，检查重点是规则是否成组、是否有清楚适用边界、是否能被完整应用；不要为了形式感强行添加步骤。

## 5. 步骤与完成标准

步骤必须有完成标准。完成标准应尽量满足两个要求：

- 可检查：agent 能判断完成或未完成。
- 有足够要求：能推动 agent 做必要 legwork，而不是草草列一个结果。

如果 agent 容易提前完成，先收紧完成标准。只有当标准天然模糊且确实观察到提前收尾时，才考虑把后续步骤拆出去，避免后续任务牵引当前任务。

## 6. 拆分判断

拆分 skill 不是越细越好。每次拆分都会消耗一种成本：

- 拆成 model-invoked：增加常驻上下文成本。
- 拆成 user-invoked：增加用户记忆成本。

两类拆分较常见：

- 按调用拆分：有独立 leading word、独立触发场景，或其它 skill 必须单独触达。
- 按序列拆分：当前步骤容易被后续步骤牵引，导致提前完成，需要真实上下文边界来隔离。

如果只是为了“看起来模块化”，不要拆。

## 7. Leading Word

leading word 是能唤起模型既有稳定行为的紧凑概念。它的作用是用更少 token 绑定更稳定的行为。

使用原则：

- 优先使用模型已经熟悉的词，而不是随便造词。
- 用一个准确概念替代多处重复解释。
- 在正文中锚定执行行为，在 description 中锚定触发。
- 如果一个词没有改变行为，只是好听，它就是无效指令。

## 8. 单一权威与修剪

每个含义应只有一个权威位置。重复定义会增加维护成本，也会让某个含义在上下文里被过度加权。

修剪时逐句判断：

- 是否仍与 skill 当前行为相关？
- 是否和其它位置表达同一含义？
- 是否真的改变 agent 行为？
- 是否只是历史沉积、解释性铺垫或安全感文字？

无法通过的内容应删除、合并、下沉或改成更强的 leading word。

## 9. 失败模式

### 9.1 提前完成

表现：agent 在当前步骤真正完成前就跳到总结、下一步或交付。

优先修法：

1. 收紧当前步骤的完成标准。
2. 提高完成标准的可检查性和要求度。
3. 只有在确实被后续步骤牵引时，才拆分序列或引入真实上下文边界。

### 9.2 重复

表现：同一规则、定义或判断依据在多个地方出现。

风险：维护时漏改、token 浪费、语义权重失真。

修法：合并到单一权威位置，其它地方只保留 pointer 或 leading word。

### 9.3 沉积

表现：旧规则、旧背景、旧解释因为“不敢删”留在 skill 里。

风险：agent 读到过时信息，主文件越来越难维护。

修法：用相关性检查清理；需要历史解释时放入治理日志，不放进执行路径。

### 9.4 蔓延

表现：主文件太长，即使每句都有用，也让 agent 难以抓住当前路径。

风险：注意力稀释、维护成本上升、上下文浪费。

修法：用信息层级下沉 reference，按分支或序列拆分路径。

### 9.5 无效指令

表现：句子没有改变模型默认行为，例如泛泛要求“认真”“清楚”“全面”。

风险：花费上下文却不提升可预测性。

修法：删除；或替换成更强、更具体、能触发行为变化的 leading word、完成标准或边界条件。

## 10. Reference-only Skill 判断

reference-only skill 的价值是提供一个稳定判断体系，而不是驱动线性动作。它可能适合作为：

- 审查准则。
- 术语体系。
- 平级规则集。
- 其它 skills 可引用的共享判断材料。

审查时问：

- 它是否需要 agent 自动触发，还是只应被其它流程按需引用？
- 规则是否共置且边界清楚？
- 是否有足够的完成标准，要求 agent 应用每条相关规则？
- 是否因为缺少步骤而无法行动，还是本来就不需要步骤？

只有当 reference 无边界、不可应用、内容沉积或需要流程却没有流程时，才把“缺少 workflow”视为问题。

## 11. 吸收时的落点判断

从 source skill 吸收设计时，按以下顺序判断落点：

1. 是否改变 `skill-siphon` 的主流程或硬闸门？如果是，才进入 `SKILL.md`。
2. 是否是通用 skill 质量准则？进入 `skill-quality.md`。
3. 是否是较完整的概念体系、术语或失败模式？进入本文件。
4. 是否是分析 source 时需要的 lens？进入 `source-analysis.md`。
5. 是否只是 source 的写法风格或领域经验？不吸收，最多在 adoption summary 记录。

目标不是复制 source，而是保留能提升 target 可预测性的机制。
